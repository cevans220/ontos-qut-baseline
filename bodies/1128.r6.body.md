## Summary

Estates were read from `data/estates.yaml` into an `EstateManager` that the route dependency created on every request. An estate created through the API was kept in that request's manager only, so `GET /api/estates/{id}` right after the create returned 404 and the estate was gone from the list. The E2E suite skipped on that (`test_21_estates`: "Estate in-memory storage does not persist across requests"). This PR stores estates in the database, as the parent PRD (#143, "Estate Persistence" and "Sharing Policies") describes.

## Changes

- Backend:
  - New tables `estates`, `estate_sharing_policies` (with `direction`: `export` or `import`) and `estate_sharing_rules` (`db_models/estates.py`, migration `b8_estates_tables`). Policies and rules keep their order (`position`) and are deleted with their estate.
  - `EstatesRepository` (`repositories/estates_repository.py`) on `CRUDBase`. Saving an estate keeps the id of a policy the payload names; a policy id the estate doesn't have gets a new row. Moving a policy between export and import (changing its direction) stores it as a new row, so the moved policy gets a new id.
  - `EstateManager` is one instance on `app.state.estate_manager` (set in `startup_tasks.py`), read by `get_estate_manager` in `manager_dependencies.py`; every method takes the request's session. Create and update record `created_by` / `updated_by`.
  - `models/estate.py`: `sharing_policies` is split into `export_policies` and `import_policies`. `SharingResourceType` is `data_product`, `data_contract`, `business_term`, `data_domain`, `concept`. The old `sharing_policies` list is still accepted on input (as export policies), and `business_glossary` is read as `business_term`.
  - A second estate with the same name is refused: 409 with `detail = {code: estate_name_conflict, message, params: {name}}` (the English message unchanged as the fallback). Two requests that both pass the name check (creating, or renaming to, the same name at once) hit the unique constraint; that error gets the same coded 409 instead of a 500, and other integrity errors are raised unchanged (14568e0d).
  - The sync route records the time and status in the database, as it did in memory; the transports of #143 are not part of this issue.
  - The create audit entry now carries the new estate's id (it was `null`).
- Upgrade path for existing deployments (new in this revision):
  - `import_estates_from_yaml_once()` in `startup_tasks.py` checks on startup if estates tables are empty; if they are and an estates YAML file exists at the old location (`data/estates.yaml`), imports estates with their policies and rules into the database, then marks the import as done via `app_settings`.
  - On subsequent startups, the import flag prevents re-importing even if all estates are deleted (supports cleanup/reset workflows).
  - Malformed YAML is logged but does not prevent startup; import is marked as done to avoid retry on every startup.
  - Supports the old `sharing_policies` field and `business_glossary` resource type for backward compatibility.
  - See `test_estates_yaml_import.py`: import scenarios, upgrade path (no duplicates on second startup), empty tables without YAML, and graceful malformed YAML handling.
- "Edit Estate" on the estate page only showed "Edit Estate functionality to be implemented". It opens the estate list with that estate's edit dialog (`?edit=<id>`), which saves through `PUT /api/estates/{id}`. A sharing rule was shown as "Filter by status where value equals 'active'" with the operator as stored; each operator now has its own whole sentence in each language, and the policy dialog's operator list is translated (2c7d36e8). Tests: three vitest cases, which fail without the commit. UI (pt and en): "Filtrar por status onde o valor é igual a 'active'", the operators "É igual a / Contém / Começa com / Corresponde à regex", and "Editar Estate" opens the dialog with the estate filled in.
- `data/estates.yaml` is removed from committed files. The file is used only for upgrade imports; sample estates are not re-imported on subsequent startups (controlled by the `estates_yaml_import_done` flag in `app_settings`). A fresh install starts with no estates.
- Frontend:
  - The estate page shows export and import policies in their own sections; "Add Policy" adds to the section it was clicked in.
  - The policy dialog offers the five resource types, translated; the policy card shows the translated type.
  - The duplicate name error is translated (`estates:errors.codes.estate_name_conflict`).
  - Types moved to `types/estate.ts` (shared by the list, detail, dialog and graph view).
- The route audit fields named in the issue (`estate.cloud`, `estate.enabled`) were already fixed on `development` (#105); nothing to change there.

i18n: new keys `estates:resourceTypes.*`, `estates:details.policies.export.*` / `import.*` and `estates:errors.codes.estate_name_conflict` in all 8 locales; the replaced `details.policies.title`, `sectionDescription` and `emptyTitle` keys are removed.

## Upgrade Path

When upgrading an existing deployment that has estates configured in `data/estates.yaml`, the import runs automatically on the next startup. Existing estates are imported into the database with all their sharing policies and rules. The import is marked as done, so deleting all estates later does not re-import the YAML. If the YAML file is malformed or missing, no import occurs; the app starts normally. See `test_estates_yaml_import.py` for test coverage of the upgrade scenario.

**How to test the upgrade:**
1. Create a test deployment with `data/estates.yaml` containing sample estates
2. Start the app; estates should appear in the database
3. Restart the app; no duplicate imports occur
4. Delete all estates; on restart, they are not re-imported (flag blocks it)
